# 图片生成任务限制规范

## 目标与口径

图片生成限制是全局配置，但额度按账号计算。`submitted`、`processing` 状态的图片任务属于“在途图片任务”；视频任务和 `completed`、`partial_completed`、`failed` 状态的图片任务不占在途额度。

- 在途上限：账号创建图片任务时实时检查。
- 每日上限：按北京时间自然日统计已创建的所有图片任务，任务后来失败也计数。
- 每日上限不追溯已有任务；本规范新增的保存约束只针对在途上限。

## 管理员保存约束

管理员通过 `save_generation_limits(enabled, max_active, max_daily) -> jsonb` 保存配置。RPC 校验管理员身份与当前有效会话，并锁定 `site_settings` 中的 `generation_limits` 行。

当限制启用时，RPC 按账号统计在途图片任务：

- 任一账号当前在途数大于拟保存上限时，拒绝保存，数据库原配置不变。
- 当前在途数等于拟保存上限时允许保存。
- 关闭限制时允许保存，不终止任务、不退款，也不处理已有任务。

冲突只返回汇总，不暴露账号信息：

```json
{
  "ok": false,
  "code": "ACTIVE_IMAGE_TASKS_EXCEED_NEW_LIMIT",
  "current_max": 5,
  "limit": 2,
  "affected_accounts": 3
}
```

成功结果使用数据库最终值刷新后台表单：

```json
{
  "ok": true,
  "settings": {
    "enabled": true,
    "maxActiveImageTasks": 3,
    "maxDailyImageTasks": 50
  }
}
```

## 并发锁关系

`save_generation_limits` 对配置行使用 `FOR UPDATE`；`create_generation_job_with_billing` 在账号级建单锁之后，对同一配置行使用 `FOR SHARE`。因此管理员保存与图片建单会按数据库取得配置行锁的顺序串行化：

- 建单先取得共享锁：保存等待建单提交，随后统计到新任务并决定是否拒绝。
- 保存先取得独占锁：建单等待保存提交，随后读取新配置并按新上限检查。

两种顺序都不能产生“降限保存成功，但提交完成后已有账号超过新上限”的状态。视频建单不读取图片限制配置，不参与这项锁关系。

## 客户端行为

后台不再直接写 `site_settings`。结构化冲突会保留当前表单值和数据库原值，并提示“当前有 N 个账号超过新上限，最高 M 个。请等待任务完成后再保存。”数据库错误沿用原错误信息。现有客户生成接口及其 429 响应格式不变。

## 发布与验证

已有数据库发布时，先执行 `docs/sql/2026-07-28-save-generation-limits-guard.sql` 这份最小幂等迁移；只有新建数据库才执行完整 `supabase-schema.sql`。随后必须使用两个数据库会话交错验证建单与降限，并覆盖以下场景：

1. 某账号有 3 个在途图片任务时，上限 2 被拒绝且配置不变；上限 3 或更高保存成功。
2. 该账号在途数降到 2 后，上限 2 保存成功。
3. 视频任务及图片终态任务不计入统计。
4. 关闭限制时允许保存，且已有任务保持不变。
5. 建单先持锁、保存后等待，以及保存先持锁、建单后等待，两种顺序均满足最终不变量。

### 生产旧版本兼容

生产库可能仍使用不包含图片限额的旧版 `create_generation_job_with_billing`。最小迁移必须先校验旧函数体指纹，再将它原样保留为内部函数，并由同签名新入口负责账号锁、限额检查和配置共享锁；指纹不匹配时整笔回滚。不得假设生产函数已经包含 `generation_limits`，也不得仅凭字符串替换覆盖未知函数版本。
